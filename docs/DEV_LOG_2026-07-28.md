# Dev Log — 2026-07-28

Board: Waveshare ESP32-S3-Touch-LCD-1.9 (320x170, ST7789 SPI + CST816 touch).
Branch: LVGL UI (`MiniWebRadio-Waveshare`), not the native-tftLib port.

This entry covers one long working session: fixing WiFi connectivity end to
end (it never actually worked before this), the crash that came from radio
playback while offline, a full redesign of the on-device + phone-web WiFi
settings flow, and rounding out the local-music lyrics feature.

## 1. WiFi never actually connected — root cause

The original complaint was simply "WiFi doesn't connect." Diagnosis went
through several wrong turns before landing on the real constraint:

- `esp_wifi_init()` was intermittently failing with `ESP_ERR_NO_MEM`.
- Moving the WiFi driver init earlier in boot "fixed" WiFi but broke audio's
  I2S DMA allocation instead — same symptom, different consumer.
- Real measurements on this board's ~110KB of internal/DMA-capable free heap
  at boot:
  - `audio.setPinout()` (I2S DMA descriptors + the audio task's own buffers)
    alone costs **~73KB**.
  - `esp_wifi_init()` needs on the order of **~35KB** more of that same pool.
  - LVGL's own display draw buffers wanted another ~25KB on top.
  - Total demand (~133KB) exceeds the ~110KB available — **structurally**,
    not from a bug that reordering or buffer-count tuning alone could fix.

Fixes applied, in the order that actually mattered:

1. **Moved LVGL's draw buffers to PSRAM** (`waveshare_lvgl_port.cpp`).
   Verified the actual display driver in use (`Arduino_HWSPI`, not a DMA-direct
   backend) already copies through its own internal bounce buffer via plain
   CPU reads before handing bytes to `SPI.transfer()` — so there was never a
   hardware requirement for this buffer to be internal/DMA-capable. This
   alone gives back ~25KB of internal RAM with no measured effect on
   smoothness (kept `kRowsPerBuffer` at its original value per explicit
   instruction to protect audio/display quality over freeing memory).

2. **WiFi now connects before audio claims memory**, not after. Audio must
   never fail (no sound is worse than a few seconds without network), so
   `connectToWiFi()` runs synchronously and boundedly (~11s worst case) at
   the *front* of `setupLvglRuntime()`, before `audio.setPinout()`. A
   background `s_f_1sec` tick still retries `wifiMulti.run()` every second
   if the initial attempt fails or the connection later drops — this no
   longer requires having succeeded once first (that gate was itself a
   latent bug: a device that never got WiFi up at boot would never retry).

3. **Tuned WiFi's own sdkconfig footprint** (`platformio.ini`'s
   `custom_sdkconfig` + the generated `sdkconfig.esp32s3_OTA`, which had to
   be hand-edited after a `custom_sdkconfig`-triggered regen wiped an
   unrelated RTC-segment tuning and broke the link): `STATIC_RX_BUFFER_NUM`
   32→4, `DYNAMIC_RX_BUFFER_NUM`→12, `MGMT_SBUF_NUM`→8, AMPDU TX/RX disabled.
   Reasonable for a single-station radio client, not a high-throughput AP.

4. **Trimmed audio's own I2S DMA footprint**
   (`audio.settings.DMA_DESC_NUM`, `ESP32-audioI2S`'s `Audio.h`): library
   default is 32 descriptors (~32KB); tried 20 (only saves ~4KB) but that
   left only ~7.7KB free after audio+WiFi init — not enough headroom for
   other runtime network activity (the weather fetch's own DNS lookup
   started failing). **Settled on 16** — noticeably better memory headroom,
   accepted tradeoff is mild crackling in local playback. Do not raise this
   further without a real reduction elsewhere to spend it on.

Net result: WiFi, audio, and LVGL now all initialize successfully together.
Verified via serial capture (free-heap logging left in at several points in
`setupLvglRuntime()` and `connectToWiFi()` for future debugging) and by
actually connecting the device to a real AP and confirming IP assignment.

## 2. Radio-playback crash while offline

Root cause, found via `xtensa-esp32s3-elf-addr2line` on the panic backtrace:
tapping next-station while WiFi was down called all the way down to
`sys_mbox_post()` inside lwIP with a null mailbox — because the TCP/IP stack
was never actually brought up (the WiFi task itself had silently failed to
even start in one iteration of the memory saga above, so nothing had called
`WiFi.mode()` yet). `Audio::connecttohost()`/`connecttohost()` had no guard
for "no network," and DNS resolution on a stack that was never initialized
segfaulted instead of failing cleanly.

Fix: `connecttohost()` (`main.cpp`) now checks `WiFi.isConnected()` first and
fails the same way a real connection failure would (`s_f_isWebConnected =
false`, increments the existing fail counter) instead of ever reaching the
network stack. This is a real, permanent guard — not just incidentally fixed
by the memory work above, since the same crash is reachable any time the
device is legitimately offline.

## 3. WiFi settings UI — redesigned twice

First redesign added on-device network scanning + a password-entry
on-screen keyboard. Along the way: fixed the keyboard being pushed almost
entirely off-screen (`lv_keyboard_create()` internally aligns
`LV_ALIGN_BOTTOM_MID`, and plain `lv_obj_set_pos()` doesn't clear that align,
so the offsets got reinterpreted from the wrong anchor — fixed by using
`lv_obj_align(..., LV_ALIGN_TOP_LEFT, ...)` instead), fixed default-theme
padding making 4 keyboard rows not fit in the available height, and
retheme'd the password field/keyboard to match the app's dark palette
instead of LVGL's default light theme bleeding through.

Second redesign, after confirming the memory root cause above: **removed
on-device scanning entirely**. The device's Settings > WiFi screen now only
ever lists saved networks (from NVS) with a "已连接"/"出厂默认" tag and a
tap-to-retry-reconnect action (nudges `wifiMulti.run()`, no password
re-entry needed since the credential is already stored). Discovering and
adding brand-new networks moved entirely to a **phone-only `/wifi_manage`
web admin page** (new endpoints in `main.cpp`'s `WEBSRV_onCommand`:
`wifi_manage`, `wifi_status_json`, `wifi_scan_json`, `wifi_saved_json`,
`wifi_connect`, `wifi_forget`), reached from the device via a QR code
("后台管理" button). This is both a UX simplification (scanning is now
on-demand from the phone page load, not a background task competing for
boot-time memory) and the direct fix for the memory pressure diagnosed above.

Also fixed along the way: the web admin page's "附近的WiFi" card template was
missing a closing `</div>`, so every scanned-network card ended up nested
inside the previous one — everything below the first row rendered as a
garbled, overlapping mess. Rewrote that section with a dedicated
`.scanCard` class instead of overloading the two-child `.card` flex row.

## 4. Local-music lyrics — from half-working to end-to-end

Prior state: local SYLT/`.lrc` lyrics worked in the narrow case where they
existed; the online-fetch path (lrclib.net) had never actually been
exercised, since WiFi had never truly connected on this device before now.

Changes:
- `LyricLine::text` grown from 80 → 160 bytes (and the SYLT-parsing raw
  buffers `textBuf`/`frameForDecode` grown to match) — real lyric lines,
  especially CJK ones re-encoded from UTF-16 SYLT text, were being silently
  truncated at 80 bytes with no warning.
- Added a `LyricFetchState` (`Idle`/`Pending`/`Found`/`NotFound`) tracked
  alongside the existing per-track lyric cache in `main.cpp`, exposed via
  `PlayerService::lyricsFetchState()`. The Local Now Playing screen now
  shows "正在联网查询歌词..." while a fetch is in flight and "未找到歌词，
  点击重试" (tappable — `HifiUi::onLyricRetryAction`, re-queues
  `lyricsFetchTask`) instead of a blanket "没有歌词信息" that gave no signal
  about whether it was still worth waiting.
- Added temporary diagnostic logging to `fetchLyricsOnline()` (the actual
  request URL and first 200 bytes of the lrclib.net response body) to debug
  why real-world lookups were coming back "not found" — **not yet resolved
  as of this entry**, see Open Issues below.

Explicitly **not** changed, per direct instruction: the lyric display stays
single-line/whole-line-swap (no scrolling/multi-line karaoke layout), and
the cassette-tape visual mode still doesn't show lyrics at all (out of
scope).

## Open issues / next steps

- **lrclib.net lookups returning "not found" for tracks that likely exist in
  the database** — diagnostic logging was added (request URL + response
  body snippet) but not yet reviewed against a real capture. Likely
  candidates: title/artist string mismatches from ID3 tag quality, or the
  query needs fuzzier matching than an exact `track_name`/`artist_name`
  lookup.
- **SYLT `tsFormat==1` (MPEG-frame-count timestamps) still unsupported** —
  confirmed via live logs to be why several tracks with embedded
  "synchronized lyrics" (per the audio library's own decode log) still
  parse to 0 lines locally. Would need the track's actual MPEG version/layer
  and sample rate at ID3-parse time (before the file is actually decoding)
  to convert frame counts to milliseconds. User explicitly asked for this to
  be fixed; not done yet.
- Local playback has mild crackling from the `DMA_DESC_NUM=16` tradeoff
  above. Only lever left to improve this without giving back WiFi's newly-
  won stability is finding a *further* memory reduction elsewhere (moving
  more of audio's own buffers to PSRAM, if the ESP32-audioI2S library
  supports it; migrating the display stack to `esp_lcd` was discussed but
  concluded to have no memory-budget benefit over the PSRAM-buffer change
  already made, since both ultimately go through the same SPI driver layer).
- Free-heap diagnostic `printfln()` calls left in `setupLvglRuntime()` and
  `connectToWiFi()` (`main.cpp`) and `waveshare_lvgl_port.cpp`'s buffer-alloc
  logging — useful for the next round of memory tuning, safe to remove once
  the budget is considered settled.
