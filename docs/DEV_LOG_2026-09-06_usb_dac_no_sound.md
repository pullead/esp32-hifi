> 分支 `codex/usb-audio-dac-20260905`。

## 1. 最贵的一条教训：「在 Windows 上验过」不等于「验过了」

9/5 那版的结论是「UAC2 声卡模式真机验证通过」。实际情况是：

| 主机 | 9/5 结论 | 9/6 实测 |
|---|---|---|
| Windows | ~~✅ 出声正常~~ **该结论系口头声称，从未实测**（2026-09-07 澄清） | （未复测） |
| macOS | 未测 | ❌ 认得出设备，零声音 |
| iOS | 未测 | ❌ 同上 |
| Android | 未测 | ❌ 同上 |

> **2026-09-07 补充更正**：上表 Windows 那格的 ✅ 后来被确认**根本没做过测试**
> ——是口头说的。所以真实情况不是「只在最宽容的主机上验过」，而是**一次都没验过**，
> 却写下了「真机验证通过」。
>
> 这让 §2.1 的根因解释变得完全自洽：回调是死函数，任何主机都不可能出声。
> 同时也说明下面这条教训还不够狠——真正的问题不只是「验证覆盖面不够」，
> 而是**把没做过的验证写成了结论**。验收标准应当是：写「验证通过」之前，
> 先能说清楚**具体做了什么操作、观察到什么现象**；说不出来就不能写。

USB 主机栈之间的**宽容度差异极大**。Windows 的 `usbaudio2.sys` 会替设备兜底
（反馈值无效时回退到标称速率、对描述符细节宽容），Apple 和 Android 则严格照
规范办事。**只在最宽容的主机上验过，等于没验过协议实现。**

下次涉及 USB / 蓝牙 / 网络协议这类「对端不受我们控制」的功能，验收标准应当是
**至少两种不同来源的主机**，且必须包含一个严格的（Apple 系最合适）。

## 2. 四个根因（按发现顺序）

排查全程串口是不可用的 —— TinyUSB 接管 USB 口后 USB-Serial/JTAG 就没了，
`printf` 一个字都抓不到。所有诊断都必须做在屏幕上，或者从**主机侧**读。

### 2.1 回调名写错，静默失效 —— 这是「完全没有声音」的根因

```cpp
// 我们实现的（旧 API 名）
bool tud_audio_rx_done_post_read_cb(...)   // ❌ 驱动里根本没有这个符号

// 这一版 TinyUSB 实际调用的
bool tud_audio_rx_done_isr(...)            // audio_device.h:251 / audio_device.c:499
```

新版把这个回调改名了，`audio_compat.h` 也**没有**给旧名提供兼容别名。用旧名的
后果是：它只是一个没人引用的全局函数 —— **编译零警告、链接正常、运行时驱动
一路调用它自己那个什么都不做的弱默认实现**。

这类错误盯着自己的代码看一百遍也看不出来，因为代码本身挑不出任何毛病。

⚠️ 后缀 `_isr` 是字面意思：它现在在**中断上下文**里被调用。所以回调里不能阻塞、
不能 `printf`、也不要做浮点运算（ESP32 的 FreeRTOS 默认不允许在 ISR 里用 FPU）。
FFT 那些浮点活儿都留在 UI 线程的 `usbDacGetSpectrum()` 里。

**排查这一条的路径**（值得复用的方法）：

1. **从主机侧确认对端行为** —— macOS 的 `ioreg` 显示 `IOAudioEngineState = 1`、
   `IOAudioStreamNumClients = 1`、流接口 `bAlternateSetting = 1`，
   即**主机确确实实在推流**。这一步直接排除掉「主机没发数据」整个方向，
   而在此之前已经在那个方向上白白试了两轮。
2. **屏幕上放原始状态位** —— `mnt/str/prm` 三个标志 + 收包计数。
   读到 `str=1` 而 `PACKETS=0`，故障就锁死在「主机在发、设备没收」。
3. **往驱动里埋点** —— 这段驱动的失败是静默的（`ep_out` 没 arm 也照样会调
   `tud_audio_set_itf_cb`），只能在 `audio_device.c` 里加一个位图记录分支走向。

第 3 步我还埋漏了一条 `#if` 分支，读出来的 `dg07` 一度被误判成「`usbd_edpt_xfer`
失败」。**恰恰是去核对这个误判**，才促使我通读驱动里 rx 回调的调用链，
发现 `grep tud_audio_rx_done_post_read_cb` 在整个驱动里一个匹配都没有。

### 2.2 全速 UAC2 的反馈格式 —— 这是「声音断断续续」的根因

USB 2.0 规范 5.12.4.2：等时反馈值 Ff 的格式由**总线速度**决定 ——
全速是 10.14 定点数 3 字节，高速才是 16.16 的 4 字节。

但 TinyUSB 的 `audiod_fb_send()` 是按 **UAC 版本**选的（UAC1→10.14，UAC2→16.16）。
UAC2 设备普遍跑高速，所以这个近似平时成立 —— **可 ESP32-S3 的 USB-OTG 只有全速**：

```
设备发 16.16：value = 3145728 (48 采样/帧) -> 小端字节  00 00 30 00
主机按 10.14 解析前 3 字节：0x300000 / 16384 = 192 采样/帧   <-- 真值的 4 倍
```

主机被告知「每帧给我 192 个采样」，这个数荒谬到它只能不停重新协商音频流：
反复 `set alt=1` → 设备侧每次都清空环形缓冲 → 声音断续、屏上状态狂闪、
缓冲水位涨到 20% 就归零。

**判断这一条的关键线索**：欠载/溢出计数**全程是 0**。说明不是缓冲策略的问题
（根本没走到欠载），是被主机的重新协商反复打断的。

修复分两处，缺一不可：
- `patches/patch_tinyusb_feedback.py` —— 把格式判据从 UAC 版本改成总线速度
- `src/usb_dac.cpp` —— 反馈端点描述符的 `wMaxPacketSize` 从 4 改成 **3**

⚠️ 补丁必须走 `patches/`：`managed_components/` 在 `.gitignore` 里，直接改那份
源码既不会被提交，也会在组件管理器重装依赖时被抹掉 —— 而症状（声音断续）和
原因（一个字节格式）相距太远，丢了之后几乎不可能再查一遍。

### 2.3 预填水位 ≈ DMA 容量，自己制造断流

```
I2S DMA 容量   = 6 x 240 帧 = 5760 字节 = 30ms
预填目标水位   = kRingBytes/4 = 6144 字节 = 32ms
```

`i2s_channel_write()` 会一直搬到 DMA 塞满才阻塞，所以 i2sTask 是**贪婪消费者**，
预填攒的 6144 字节一上来就被 DMA 吸走 5760。ring 立刻见底 —— 而旧代码**一读空
就 `s_primed = false` 退回预填**，回去攒 32ms，可 DMA 只撑得住 30ms → 断音。
攒够再放、再被吸干、再断。

9/5 的日志 §4.8 其实已经写对了道理（「抽空缓冲是稳态下的正常现象」），但修复
只改了**计数条件**，没动**退回预填**这个动作 —— 注释和代码是矛盾的。

正确判据：**连续空到超过 DMA 撑得住的时间**才算真断流（现在是连续 40 次 x 1ms）。

### 2.4 MSC 接口在声卡模式下也被枚举

`USBMSC` 的**构造函数**里就调了 `tinyusb_enable_interface(USB_INTERFACE_MSC, …)`
（arduino-esp32 `cores/esp32/USBMSC.cpp:204`）—— 只要那个对象存在，MSC 描述符
就无条件进配置描述符，跟有没有调 `begin()` 毫无关系。

它原本是 `main.cpp` 里的文件级全局对象，于是声卡模式下设备在主机眼里是个
**MSC + Audio 复合设备**（macOS `ioreg` 实测：接口 0 是 TinyUSB MSC、接口 1 才是
音频），既违背「一个 USB 口同时只能是一种用途」的设计，MSC 的 bulk 端点还白占
USB-OTG 的 DFIFO。

改成函数内 static（C++11 magic static，线程安全的延迟构造），声卡模式下永不构造。

**注**：这一条**不是**没声音的原因 —— 修完之后 `PACKETS` 依然是 0。但它是个真实
缺陷，而且排除掉它才让后面的判断少了一个变量。

## 3. 界面：三段式重做

按「移植本地音乐播放界面」重做，几何**完全对齐 Radio Now Playing**（三个页面
并排看过去应该是同一台机器的三种工作状态，不是三套界面）：

| 位置 | Radio 页 | 声卡页 |
|---|---|---|
| 顶栏左上 | 返回 | **退出声卡模式**（唯一退路） |
| 顶栏右侧 | 时间 / WiFi | 链路指示（圆点 + 已连接/未连接） |
| 封面 72x72 | 电台图标 | **采样率信息块**：PCM 铭牌 + 大号采样率 + 位深声道 + 静音角标 |
| 封面下 (0,79) | 9 段 VFD 电平梯 | 同左，位置逐像素一致 |
| 其下 (0,92) | L/R 峰值 dB | 同左，位置逐像素一致 |
| 点阵频谱 (80,39) | 解码器 6 段 FFT | **USB PCM 自算的 6 段 FFT** |
| (80,91) | 流缓冲活动条 | 环形缓冲水位（含义正好对应） |
| 底栏 6 按钮 | 走带控制 | **信息栏** BUFFER / LATENCY / UND-OVR / PACKETS |

### 3.1 频谱：数据源与两个坑

声卡模式拿不到 `Audio::getSpectrumBands()`（那是**解码器**算的，而这里 PCM 不经过
解码器），只能自己算：rx 回调里只把样本抄进 512 点环形快照（纯 memcpy，不做计算），
FFT 由 **UI 线程（core 0 之外）** 在 `usbDacGetSpectrum()` 里做。

- **坑一：忘了归一化。** N 点 FFT 对幅度 A 的正弦，bin 峰值是 `A*N/2`，加 Hann 窗
  后是 `A*N/4`。直接拿原始值算 dB，幅度 0.5 的信号能算出 +36dB，映射完远超 255
  → **所有频段恒满格** → 28 列全部点满 → 逐列脏检查发现「和上次一样」整列跳过重绘
  → 屏幕上看起来是**频谱死住不动**。归一化系数 `4/N`（`2/N` 的 FFT 归一化 x 2 倍
  Hann 窗增益补偿）。
- **坑二：不能照抄本地播放页的 `level * 1.5f`。** 那个 1.5 倍是给
  `getSpectrumBands()` 做补偿的，而这里的数据已经是真实幅度，再乘 1.5 等于
  -3.5dB 就顶满。

dB 映射最终取 **-60dB..+6dB → 0..255**，上限留 6dB 余量，满刻度信号落在约九成高度。

### 3.2 字体：两类乱码，原因不同

- 往 **Montserrat** 标签里塞中文 → 整行豆腐块。LVGL 内置 Montserrat 只有基本 ASCII。
- 往 Montserrat 里塞 **`·`（U+00B7 中点）** → 单个方框。这个更隐蔽，
  `UAC2 · ASYNC` 和 `16BIT · 2CH` 都栽在这儿。

动态中文一律用 `HIFI_FONT_DYNAMIC_TEXT`（`lv_font_cjk_13`）；
`lv_font_cjk_16` 是子集化字体，只包固定标题字形（见 `hifi_fonts.h`）。

### 3.3 退出键：只放大热区，不动 UI

26x20 在这块电容屏上实测常常要点好几次才中。用 `lv_obj_set_ext_click_area(btn, 12)`
把**可点区域**扩到 50x44，绘制尺寸和版面一点不动。

同时**屏蔽了声卡页的左滑边缘返回**：退出声卡模式要重启整台机器（TinyUSB 只能开机
启动），代价远高于普通翻页，不能让一次误触把正在放的音乐整个打断。这两件事是配套的
—— 关掉左滑之后，顶栏那颗键就是唯一退路，所以它更不能难点。

## 4. 顺带修掉的

- **`i2sStart()` 的 use-after-free**：原来控制回调（TinyUSB 任务）直接调它，
  而它开头就 `i2s_channel_disable` + `i2s_del_channel`，此刻 i2sTask 可能正阻塞在
  `i2s_channel_write()` 里用着同一个句柄。改成控制回调只记下目标采样率，真正的重配
  由 i2sTask 在自己循环里做 —— **句柄只被一个任务碰，竞态从根上不存在**。
  Windows 之所以没炸：它默认就是 48000，和初值相同，从没走到过重配路径。
- **反馈值在开流瞬间是 0**：`tud_audio_set_itf_cb` 里补上标称值。
  （注：这个改动本身没有解决任何观察到的问题，但它是对的 —— 主机在 alt=1 后会先读
  反馈端点。）

## 5. 排查方法论：这一轮真正起作用的三件事

前面兜了好几个圈子（先后押注「反馈值初值为 0」和「i2sStart 竞态」，都改了、都没用），
转折点不是想得更清楚，而是**开始测量**。三条经验值得固化下来：

### 5.1 先从**对端**确认，不要从自己这边猜

`ioreg -l -w0 -r -n "MiniWebRadio DAC"` 一条命令就回答了「主机到底在不在发数据」：

```
IOAudioEngineState      = 1    引擎运行中
IOAudioStreamNumClients = 1    有程序在推流
bAlternateSetting       = 1    流接口已开
```

这直接砍掉了「主机没发」这**整个方向**——而在此之前已经在那个方向上白试了两轮。
USB / 蓝牙 / 网络这类有对端的功能，对端的状态往往比自己这边好查得多，
应该**第一步**就去看，而不是最后。

macOS 侧还有两条也很有用：
- `system_profiler SPUSBDataType` —— 设备有没有枚举、VID/PID、供电协商结果
- `system_profiler SPAudioDataType` —— 有没有被当成音频设备、**是不是当前默认输出**
  （踩过：设备一切正常，只是系统输出压根没切过来，看起来跟「设备坏了」一模一样）

### 5.2 屏幕上要有**原始状态位**，不是只有结论

`mnt/str/prm` 三个标志 + `PACKETS` 计数，比任何一句「等待主机连接」都有用。
读到 `str=1` 而 `PACKETS=0`，故障立刻锁死在「主机在发、设备没收」这一环 ——
而这两种状态在只显示结论的界面上长得完全一样。

声卡模式下这一点尤其关键：TinyUSB 占了 USB 口，串口控制台没了，**屏幕是唯一的仪表**。

### 5.3 一个反直觉的收获：诊断埋点埋错了，也能帮上忙

往 TinyUSB 里埋位图那次，我漏了一条 `#if` 分支，读出来的 `dg07` 一度被误判成
「`usbd_edpt_xfer` 失败」。**恰恰是回头核对这个误判**，才逼我通读驱动里 rx 回调的
整条调用链，进而发现 `grep tud_audio_rx_done_post_read_cb` 在整个驱动里一个匹配都没有。

教训不是「埋点要仔细」（当然要），而是：**当测量结果和推理对不上时，先怀疑测量本身**，
而核对测量的过程往往会把真正的问题顺带翻出来。

### 5.4 数字比听感更早给出答案

24bit 那次（见 §6.2），症状是「只剩沙沙声」。白噪的可能原因太多了 ——
位序、字节序、时钟、对齐都会导致白噪，光靠听大概率要试好几轮。

但屏幕上的 **LATENCY = 110ms** 一个数就够了：

```
(110ms - 30ms DMA) x 288 字节/ms ≈ 23000 字节 ≈ 环形缓冲容量 24576
```

缓冲堆满 = 消费比供给慢，而供需比正好是 **3:4** —— 和 24bit/32bit 的字节数之比
一模一样。范围立刻缩到「I2S 每帧实际吃几个字节」这一个问题上。

底栏那几个诊断数字就是在这一刻挣回本钱的。

## 6. 做了又回退的（代码在，将来可以接着做）

以下两块都实现完了，但**没有验证通过**，本轮结束前已从主线回退。
备份见本次会话的 scratchpad；要捡回来的话，下面记的是接着做需要知道的东西。

### 6.1 输出级 DSP（音量 / 三段 EQ / 平衡）

**动机**：下拉菜单里的音量和 EQ 在声卡模式下**没有任何作用** —— 那两个控件调的是
`Audio` 对象（解码器输出级），而声卡模式的 PCM 从 USB 直接进 I2S，
**根本不经过 `Audio`**，这条链路上没有它们的作用点。这不是 bug，是架构决定的。

**实现**：在 `i2sTask` 里加一级 DSP（数据即将进 I2S 的最后一站）：
- 音量走平方曲线（线性刻度下半程几乎听不出变化）
- 三段 EQ 用 RBJ cookbook 的低搁架 200Hz / 峰值 1kHz / 高搁架 4kHz，
  分频点与 `Audio` 库那三段接近，换音源时听感不跳
- 平衡只衰减一侧、不提升另一侧，避免削波
- EQ 提升后必须限幅：溢出回绕的爆音比削波难听得多
- **全平且满音量时整级旁路**（`s_dspActive = false`），保持 bit-perfect 直通 ——
  这对声卡这种设备是该有的取舍
- 由 `main.cpp` 的 `playerCoreSetVolume/SetMuted/SetToneSettings` 转发，
  并在进声卡模式时同步一次当前值（否则开机是满音量、EQ 全平，要手动动一下才对得上）

⚠️ **必须放在 `i2sTask`，不能放 rx 回调**：那个回调现在是 ISR 上下文（`_isr` 后缀），
ESP32 的 FreeRTOS 默认不允许在中断里做浮点运算。

**未验证的原因**：和 24bit 一起烧，被 24bit 的故障盖住了，没能单独确认。

### 6.2 24bit 输出

**动机**：加了 EQ 之后，16bit 下做数字衰减和滤波会吃掉有效精度；
24bit 时量化误差落在低 8 位（本来就是补零的填充位），这一级基本无损。
全速 USB 带宽也放得下（294 字节/帧，上限 1023）。

**实现涉及九处**：每采样字节数、等时端点包大小(196→294)、`tusb_config`、
描述符格式、I2S 位宽、环形缓冲格式、rx 回调的 VU/频谱取样、DSP 处理位宽、UI 显示。

**踩到的坑（这是接着做时最该知道的）**：

`I2S_DATA_BIT_WIDTH_24BIT` 决定的是**内存里每个采样占几个字节**，而不只是有效位数：

| 配置 | 内存中每采样 |
|---|---|
| `I2S_DATA_BIT_WIDTH_24BIT` | **3 字节，紧凑排列** |
| `I2S_DATA_BIT_WIDTH_32BIT` | 4 字节 |

我按 24BIT 配置、却按每采样 4 字节送数据 —— I2S 每秒只消费 288000 字节而我们在送
384000，`i2s_channel_write` 持续阻塞、环形缓冲堆满（LATENCY 50→110ms），
同时 4 字节数据被当 3 字节解析 → 纯白噪。两个症状同一个原因。

**改用 `I2S_DATA_BIT_WIDTH_32BIT` 之后**（24bit 数据左对齐放高位、低 8 位补零，
PCM510x 只取高 24 位）：白噪消失、LATENCY 回到 40-43ms 正常区间，
**但变成了完全无声**。到这一步没有继续查，两个待查方向：

1. **时钟比例**（主要嫌疑）：16bit→32bit slot 让 BCLK/LRCK 从 32xfs 变成 64xfs
   （3.072MHz）。板子上那颗 PCM510x 是无 MCLK 模式（`mclk = I2S_GPIO_UNUSED`，
   靠内部 PLL），如果它在 BCK-only 模式下锁不住 64xfs 就会安静地不出声 ——
   而 ESP32 这边照发不误，所以 LATENCY 看起来完全正常。
   验证办法：改用 24BIT + 紧凑 3 字节（BCLK 回到 48xfs），代价是 DSP 要按 3 字节重写。
2. **数字增益被归零**：当时 DSP 也在链路上，音量若为 0 同样是无声。
   下次应当**先单独验证 24bit（DSP 全旁路），再叠加 DSP** —— 这次两个一起上，
   症状混在一起，多花了一轮。

### 9.2 Windows 回归：反馈端点 `wMaxPacketSize=3` 被 usbaudio2 跳过

**这是 9/6 那轮引入的回归** —— 9/5 版在 Windows 上能正常枚举出设备（有截图为证），
9/6 把反馈端点的 `wMaxPacketSize` 按规范从 4 改成 3 之后就坏了。

现象很容易误判成"没枚举"：

- 板子屏幕显示**已连接**（`tud_mounted()` 为真 → 主机确实下发了 SET_CONFIGURATION）
- 设备管理器里**没有黄色感叹号**（它不在「其他设备」下，而是在音频类别里）
- 但声音输出列表里没有这台设备

**从 Windows 侧查才看得清**（这套命令值得复用）：

```powershell
# 1) 设备在不在、什么状态
Get-PnpDevice -PresentOnly | Where-Object { $_.FriendlyName -match 'MiniWebRadio' } |
    Select-Object Status, Class, Problem, ProblemDescription

#   -> Status=Error  Class=MEDIA  Problem=10  "This device cannot start. (Code 10)"
#      DEVPKEY_Device_Service = usbaudio2   <- 驱动绑对了，是启动失败

# 2) 驱动为什么拒绝 —— 这一步给出了确切答案
Get-WinEvent -FilterHashtable @{LogName='System'; StartTime=(Get-Date).AddHours(-3)} |
    Where-Object { $_.ProviderName -match 'usbaudio' }
```

事件日志原话：

> **The driver could not find a feedback endpoint for an asynchronous data OUT
> endpoint on device ...**

即：数据 OUT 端点声明为异步，但 `usbaudio2.sys` **找不到配套的反馈端点**。
描述符里那个端点是存在的、`bmAttributes` 也对（ISO | NO_SYNC | EXPLICIT_FB = 0x11），
唯一改过的就是包大小。

**根因**：Microsoft 的 `usbaudio2.sys` 内部一律按 **4 字节**处理反馈值
（不实现全速的 10.14 变体，是已知的互操作问题），声明 3 字节的反馈端点会被它
直接跳过。

**修复（同时满足两边）**：描述符声明 `wMaxPacketSize = 4`，实际**仍然发 3 字节的
10.14**（`patch_tinyusb_feedback.py` 不动）。等时 IN 端点发短包是合法的，声明 4
只表示"最多能装 4"：

- Windows 看到端点能装 4 → 肯启动
- 规范侧主机收到 3 字节短包 → 按全速规矩解析，仍然正确

现实中大量全速 UAC2 设备都用这个折中。

> ⚠️ **改这里必须两边都复测**：Windows 看设备能否出现在声音输出列表；
> macOS/Android 看声音是否仍然连续（反馈格式错会表现为断断续续，见 §2.2）。

**方法论补充**：§5.1 说的"先从对端确认"这次又一次奏效，而且比 macOS 那轮更彻底 ——
Windows 的 `Get-PnpDevice` + `Get-WinEvent` 直接把失败原因用人话打印了出来。
遇到"设备认不到"这类问题，**先去问主机为什么拒绝**，不要从自己的描述符开始猜。

### 9.3 iPhone 音量滑块无反应：主机音量根本没被应用

`s_volumeDb256` 只是被**存下来、并在主机来读时原样回报**，
**从来没有作用到 PCM 上**：

- `usb_dac.cpp` 主机下发 → 存进变量
- 主机读取 → 原样返回
- 中间没有任何一处把它乘进音频数据

（`s_muted` 是有效的 —— rx 回调里把 buffer 清零，所以静音能用、音量不能用。）

**这解释了 Android 正常而 iOS 不正常**：

| 主机 | 音量策略 |
|---|---|
| Android | **主机侧衰减** —— 送过来的 PCM 已经调过音量，设备做不做无所谓 |
| iOS | **送全幅 PCM**，期待设备按 Feature Unit 的值自己衰减 → 我们没做 → 滑块无效 |

这正是 §6.1 那块"做了又回退"的输出级 DSP。**只把音量那部分捡回来就能修好 iPhone**，
EQ / 平衡可以先不动。

⚠️ 必须放在 `i2sTask` 里，**不能放 rx 回调** —— 那个回调现在是 ISR 上下文
（`_isr` 后缀），ESP32 的 FreeRTOS 默认不允许在中断里做浮点运算。

⚠️ 另一个要点：UAC2 的音量单位是 **1/256 dB**，不是线性刻度。换算成线性增益是
`10^(dB/20)`，直接把这个 int16 当线性系数用会完全不对。

### 9.5 Windows 修复已确认 + 退出后 USB 消失的真正原因

**Windows 回归修复：实测通过。** 描述符 `wMaxPacketSize` 3 → 4（实际仍发 3 字节
10.14）之后：

```
Status = OK      Problem = CM_PROB_NONE     "This device is working properly"
Class  = MEDIA   + AudioEndpoint「ヘッドホン (2- MiniWebRadio DAC)」
```

电脑播放时板子屏幕上的频谱正常跳动。（修复前是 `Status=Error` / `Problem=10`。）

⚠️ 仍未复测：macOS / Android 的声音连续性。这次改的是**所有主机共用**的描述符
字段，"声明 4、发 3 对规范侧主机无害"目前只是推理。

**退出后 USB 消失 —— `usb_persist_restart` 那个修复是无效的（见 §4.9 的更正）。**

2026-09-07 实测复现：点「退出声卡模式」→ 板子重启 → **烧录没反应**，必须
**按住 BOOT 插数据线**串口才回来；而且烧录完成后不会自动重启，要手按 RESET。
（后半段是正常的：手动按 BOOT 进下载模式后，esptool 的 RTS 复位序列对
USB-Serial/JTAG 不总是生效。）

根因：`usb_persist_shutdown_handler()` 整个函数体包在
`if (usb_persist_mode != RESTART_NO_PERSIST)` 里，我们传的恰好是那个空操作分支。
而 USB PHY 归属位在 `RTC_CNTL_USB_CONF_REG`（**RTC 域，软复位不清除**），
所以重启后 PHY 仍归 USB-OTG。

可行的修法（**未实现、未验证**）：重启前自己清掉那几个 RTC 位，复刻
`usb_switch_to_cdc_jtag()` 里的关键动作：

```c
CLEAR_PERI_REG_MASK(RTC_CNTL_USB_CONF_REG,
    RTC_CNTL_SW_HW_USB_PHY_SEL | RTC_CNTL_SW_USB_PHY_SEL | RTC_CNTL_USB_PAD_ENABLE);
CLEAR_PERI_REG_MASK(USB_SERIAL_JTAG_CONF0_REG, USB_SERIAL_JTAG_PHY_SEL);
```

⚠️ 这是寄存器级改动，风险有界但真实：改错的最坏结果就是现在这个状态
（USB 上认不到，按 BOOT 可恢复），不会变砖。
