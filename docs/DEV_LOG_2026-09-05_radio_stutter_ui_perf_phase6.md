## 1. 电台卡顿：用户的一句话定位了根因

用户反馈：**后台下载时电台明显卡顿，本地音乐不卡。**

**"本地不卡"这半句是全部线索的关键**，它一句话排掉了我最怀疑的方向：

- 若瓶颈在 **SD 争用**：本地播放读 SD、下载写 SD，该卡的是**本地音乐**；
- 而电台**根本不碰 SD**；
- 现象正好相反 ⇒ **机制不在 SD**。

### 1.1 机制：DMA 内部 RAM 被压到 160 字节

前一天补的"基线 vs 下载中"对照字段第一次派上用场：

| | 空闲基线 | 下载中 |
|---|---|---|
| DMA 空闲总量 | 5616 B | **836 B** |
| **最大连续块** | 4352 B | **160 B** |

WiFi 接收路径需要 DMA 可用的内部 RAM —— 而这正是**电台依赖、本地 SD 播放
不依赖**的东西。

⚠️ 这是**测到的相关性 + 合理机制，不是证明**。
（此前猜的是 TLS 解密抢 CPU，证据不如这条强。带宽早就排除：
电台 16KB/s + 下载 23KB/s 对 WiFi 毫无压力。）

### 1.2 两层处置

**策略层**（`daily_sync.cpp`）：电台在播就**不开新的下载**，最多等 10 分钟，
还在播就推迟这一轮。每日同步有 24 小时可用，用户的听感只有一次。

**安全网**（`download_manager.cpp`）：下载**途中**电台才起播时，限速到 6KB/s。
不硬停 —— 长时间闲置会被服务器关连接，反而让已下的部分白费。

⚠️ **推迟 ≠ 今天跑过了**，所以不记 `lastRunDay`，主程序 15 分钟后重试。
否则用户听一下午电台就等于当天曲库完全不更新。

### 1.3 验证

| 项 | 证据 |
|---|---|
| 6KB/s 限速生效 | 3416KB / 570931ms = **6.0 KB/s**，与设定精确吻合 |
| 电台在播时不开新下载 | 200 秒内 `attempts` 冻结在 3 不动 + `deferring` 日志 |
| 用户听感 | 确认改善 |
| **限速下仍会触底** | `zero=9 maxrun=3` —— **限速能减轻但不能消除**，这正是要策略层的理由 |

### 1.4 前一天"影响为零"的结论是错的

`DEV_LOG_2026-09-04` §2.2 记的 `zero=0` 之所以没测到，是探针有两个缺陷：

1. **采样只在 `audio.isRunning()` 为真时进行** —— 卡顿瞬间该标志若变假，
   那些样本会被直接跳过，**测量在系统性排除它本该捕捉的现象**。
2. **100ms 采样间隔太粗** —— 一次可闻的欠载只需几十毫秒。

`zero=0` 的真实含义是"**在采样时刻**没观测到归零"，我当成了"没发生过欠载"。

### 1.5 一个转述错误

我把用户说的"很卡"记成了"挂了 / 点击无反应"，并据此在前一篇写了一整节假设。
**错误的现象描述会把排查引向"起播失败/连接建立"，方向完全不同**，
而真实现象里"电台卡、本地不卡"这个差异恰恰是定位的关键。

**教训：转述用户反馈时不要替他把话说重。**

## 2. `rtc` 恒 false —— 影响面比想象大得多

`[SYNC][STATE] idle rtc=0 ...` 一直挡着每日同步。

### 2.1 根因：成员被局部变量遮蔽

`RTIME::hasValidTime()` 读的是**成员** `timeinfo.tm_year`，而本工程每秒调用的
`RTIME::gettime_s()` 内部把 `now` / `timeinfo` 声明成了**局部变量**：

```cpp
const char* RTIME::gettime_s(){
    time_t now;            // ← 局部，遮蔽成员
    struct tm timeinfo;    // ← 局部，遮蔽成员
```

于是成员 `timeinfo` 永远停在构造时全零，`tm_year = 0` ⇒ **恒返回 false**。

### 2.2 影响

| 位置 | 后果 |
|---|---|
| `dailySyncDue()` | 恒 false ⇒ **生产状态下每日同步一次都不会跑** |
| 播放事件时间戳 | 恒 0 ⇒ `lastPlayedAt` 永远不写 |
| 扫描时间戳 | 恒 0 ⇒ **所有 `importedAt` 都是 0** |
| 闹钟 | 条件带 `&& s_f_rtc` |

后两条会让 Cleaner 的淘汰评分（按"多久没听""何时导入"）**完全退化**。

**修法**：改用仓库里早就为时钟显示采用过的判据 —— 直接看真实 epoch。
当时那次只修了显示，没修 `s_f_rtc`。验证 `rtc=1 epoch=1788570134 due=1`。

### 2.3 排查中的一次误判

我**先否定了代码里已有的那条注释**（"RTIME 缓存不刷新"），理由是
"`gettime_s()` 每秒都在调用"。**那个反驳是错的** —— 我确认了"有 getter
被调用"，却没确认"那个 getter 会不会更新成员"。注释是对的，我查错了层次。

## 3. 索引重复 + 假 missing —— 路径大小写

现象：重启后 `tracks=62 loaded_at_boot=59 missing=3`，同一首歌存了两份。

诊断打印出两份记录的路径，一眼看清：

```
MISSING path="/music/tracks/jamendo_1932670.mp3" id=3746452960 prov=1 flags=0x0C
present path="/Music/tracks/jamendo_1932670.mp3" id=1692487488 prov=0 flags=0x00
```

`daily_sync` 硬编码写 `/music`（小写），SD 上目录真名是 **`/Music`**。
FAT **查找不区分大小写**，所以下载和播放都正常；但 `entry.path()` 返回磁盘上
真实的大小写，两串的 FNV-1a 不同 ⇒ `localId` 不同 ⇒ 一份判 missing、
一份当新曲追加。

**后果比"多 3 条"严重**：扫描新增的那份 `provider=local` 且**没有 Discovery
标记**，Cleaner 会当成用户自己的歌**永不淘汰** —— 曲库轮换的前提就废了。

**修法**：`libraryHashPath()` 改为**不区分大小写**，`kLibraryFormatVersion`
1→2 强制重建索引清掉已有重复。
不改成"把 `/music` 写成 `/Music`"：那只是把硬编码换个方向，换张卡就复发。

验证：`tracks=59 loaded_at_boot=0 missing=0`（62 − 3 重复）。
代价：播放统计清零（当时 fav=0、played=13，可接受）。

### 3.1 自愈：让文件名可还原元数据

中途换固件时同步还在跑，索引从未落盘。下次开机扫描把那些文件当普通本地文件
收进索引，于是**重复下载** + **丢 Discovery 标记**。

修法不是更频繁存盘（750KB × 10 太重），而是**让文件名可还原元数据**：
`jamendo_<id>.mp3` 本来就编码了 provider 和 id，扫描时反推。
索引由此退化成缓存而不是唯一真相。

⚠️ 第一版只做了新记录反推，**对已经错了的记录无效**（`upsert` 刻意不覆盖
provider/flags）。补了定向修复：**只在现有记录压根没有 `providerTrackId`
时才填**，绝不覆盖已有值。验证：12 首全部 `prov=1 flags=0x04`。

```
[SYNC] en try#1/2/3 ok ... 16073KB 548325ms
[SYNC] done: got=3/3 attempts=3 owned=0 failed=0 empty=0 deferred=0
[SYNC] index saved (59 tracks)
```

每日闸门 + NVS 持久化也验证：重启后 `day=20701 last=20701 due=0`，不重跑。

### 5.1 语言配额 → 风格配额

用户提出改用风格（流行/摇滚/hiphop）并要求抽取近期热门。
按"先验证 API 再设计"的教训，PC 侧先摸清：

| 查询 | 结果 |
|---|---|
| `tags=pop` / `rock` / `hiphop` | 各 5/5 全部可下载，无警告 ✅ |
| `order=popularity_week` | 返回 2025,**2014,2015,2021,2010** ❌ 是累积热度 |
| `order=releasedate_desc` | 最新但完全不筛质量 ❌ |
| **`popularity_week` + `datebetween=近一年`** | 2025-11,2026-06,2026-04,2026-03 ✅ |

**"热门"在 Jamendo 上默认是累积热度，和"近期"是两回事，必须两个参数一起用。**
滚动窗口用 RTC 算 —— 依赖 §2 刚修好的 `s_f_rtc`，它之前恒 false 的话
这个设计根本落不了地。

弃用语言维度的理由：实测 `lang` 过滤名不副实 —— `lang=zh` 的 6 条里
**只有 1 条真是中文**（"凌晨三点的便利店 - 小风啊哈"），其余是 ProleteR、
Prorock 之类。

### 5.2 offset 回绕：判据用错了量

第一版写 `n < limit ⇒ 翻到池尽头`，实测**恒成立**：

```
请求 limit=20 → API 给 20 条 → 其中 1 条 audiodownload_allowed=false
→ 解析器过滤后返回 19 → 19 < 20 → 每次都"到底" → offset 永远停在 0
```

**根因**：`n` 是**过滤后**的数量，"分页到底了吗"必须看 **API 返回的原始条数**。
两个量被我当成了同一个。

后果不显眼但严重：每个风格的候选池被永久锁死在第一页 19 首，offset 推进
**完全失效**，而且失效得很安静（靠"已拥有"跳过仍能下到不同的歌）。

**修法**：`MusicProvider` 加 `lastRawCount()`；判据改 `raw < limit`；
offset 按**请求条数**推进。加日志让差异可见（此前两个量在串口上完全同形）：

```
[JAMENDO]   (raw=20, 1 filtered out as not downloadable)
```

验证 `offset=0 → 20 → 40`。

### 5.3 间歇性空返回是全 API 范围的

```
不带 lang 连打 6 次: 3,3,3,0,3,3
lang=ja  连打 3 次:  0,0,3
lang=zh  连打 3 次:  3,3,0
```

约 15~30% 的请求返回 `results_count=0`、`status=success`、无警告，**与参数无关**。
现有重试（3 次、间隔 5 秒）正好对症 —— 连续 3 次都空约 2.7%。
**这是碰巧设计对了，不是预见到了这个分布。**

⚠️ 我第一次只打一发就下结论（`lang=zh` → 0 条 ⇒ "果然没有中文歌"），
**又是 n=1 当结论**。连打几次才看清。

## 6. UI 流畅度治理（用户明确要求：流畅度优先，简约，不占资源）

### 6.1 先量化，再动手

滚动时实测：

```
flush/s=65~217   busy=29%~88.8%   max_call_us≈42000~47600
timer_handler_calls/s=65~271（空闲时 ~450）
```

**单次 `lv_timer_handler()` 最长阻塞 47ms** —— 这 47ms 内既不采样触摸、
也不出新帧，相当于卡掉 3 帧。实际帧率只有约 27fps（设定 62），
**触摸采样被压到约 25Hz**（设定 66Hz）。

**所以"提高触摸采样率"这个方向直接出局** —— 不是配置不让，是 handler 没空回来。
`flush/s=217 × 10KB ≈ 2.2MB/s`，而 80MHz SPI 理论约 10MB/s ——
**SPI 只用两成，卡在 CPU 渲染**。

### 6.2 逐项 A/B

| 改动 | 依据 |
|---|---|
| 行圆角 10 → 4 | A/B 实测：radius=0 时 `max_call` 42~47ms → 21~30ms。圆角遮罩成本约正比于半径平方，取 4 保住观感 |
| 删掉伪粗体副本 | 每行标题**每帧渲染两遍**（右移 1px 叠一份假装粗体），纯浪费 |
| 两行 → 单行 | 每行少一个文本标签，字形渲染量**减半** |
| 删掉封面小图标 | 信息价值很低，每行少一个标签 |
| 行距 44 → 32 | 可见行数 2.9 → **4.25 行** |

结果：`max_call` **42~47ms → 30~34ms**，`busy` 60~89% → 29~61%。

### 6.3 `LV_DISP_DEF_REFR_PERIOD`：改错又改回

曾从 16 改到 20ms，理由是"列表反正只有 27fps，16ms 兑现不了"。
**那个理由只看了列表。** 单独测频谱页：`busy` 仅 12~15%、`max_call` 11~20ms，
**完全不是渲染瓶颈** —— 20ms 只是把它从 62fps 白白压到 50fps。
而列表每帧要 ~30ms，16 还是 20 对它都超预算、没区别。
**维持 16ms：频谱受益，列表无损。**

### 6.4 滚动误触：三条判据，逐条补

用户反馈滑动列表时会误触发播放。

| 判据 | 覆盖的情况 |
|---|---|
| 1. 按下/松手之间列表滚动过 | 普通拖动 |
| 2. 按下前 300ms 内滚动过（"点停滑行"） | 点一下停住惯性滑行 —— 两个位置几乎相同，被判成点击。**惯性调大后这个漏洞被放大** |
| 3. **手指实际位移 > 8px** | ① 列表顶/底边缘拖动（到头了，手指在动但 `scroll_y` 不变）② 横向拖动（列表只允许竖直滚动） |

**第 3 条才是最直接的信号** —— 前两条都从"列表滚动了多少"间接推断，
在边缘和横向两种情况下会脱节。

验证：纯滑动一整轮抓取，`[PLAY][T]` 与 `[COVER]` 一行都没有，**零播放**。

顺带修一个漏掉的：`onMusicGroupAction`（歌手/专辑行）**根本没接守卫** ——
分组行挂了 arm，处理函数却没检查。又是"修好一处没顺手看同类的另一处"。

### 6.5 点按反馈：走过两次弯路

1. `addPressFx`（按下即高亮）—— 滑动时手指经过的每一行都闪一下。
   那是 LVGL 的正确行为：按下进 PRESSED，滚动一开始又清掉。
2. 给 PRESSED 加 90ms 过渡延迟，想用"停留时间"区分点按和滑动。
   **判据本身就错**：滑动往往是"按住→停顿→再移动"，停顿超过 90ms 照样亮。
   **时间分不出意图。**

最终：**只在滚动守卫判定为点击之后才高亮**。滑动时永远不亮。

### 6.6 卡一下：事件落盘在 UI 线程

滚动时每 10 秒左右出现 181~413ms 的阻塞，形态是"刷屏很少却占满 CPU"。

根因：`main.cpp` 的 1 秒节拍里 `libraryFlushEvents()` 往 SD 追加事件
（开/写/关 + FAT 元数据）。

**这是同一个坑的第三次变形**：Phase 1 因为在播放启动路径里写 SD 把播放搞挂，
改成队列缓冲；但**队列的落盘本身一直还在 UI 线程上**。

修法不动 SD 访问模型，只把落盘**推迟到用户松手之后**（手指离屏 600ms 内不写）。

⚠️ 排查中的两次误判，都写进了注释：
- 断言是 `libraryCleanerAssess` 实时读 SD —— 查调用点才发现那是扫描时的快照。
  **在没确认调用点的情况下就说"找到了"。**
- 怀疑是 10 秒周期诊断日志 —— 做了**关闭对照实验**，尖峰照旧，排除。

### 6.7 `LONG_DOT` 不是"单行截断"

用户两次反馈长标题显得杂乱，我两次回答"省略号已经有了"——**都是错的**。

> `LV_LABEL_LONG_DOT` 按标签**宽度自动换行**，只有文字超出标签**高度**时
> 才在末尾打点。

这些标签都没设高度（按内容自适应），所以长标题**永远不会打点，只会换成两行**，
在 28px 的行里挤成一团。

我只核对了长度模式、**没核对它依赖高度**。修法：把高度锁成一行
（`lv_font_get_line_height`），三处都改。

## 7. Phase 6：收藏 + 视图 + 后台可见性

### 7.1 ★ 收藏按钮（正在播放页）

底层 `playerCoreSetTrackFavorite()` 早就写好（走事件日志，不为翻一个 bit
重写 800KB 索引），但在此之前**没有任何地方调用它**，是一段死代码。

收藏的意义是**保护曲目不被 Cleaner 淘汰** —— 在真实删除开启之前必须先有
这个入口，否则用户没有任何办法保住想留的歌。
**这就是它排在 Phase 2 真实删除前面的原因**（编号更小不代表能先做）。

放在正在播放页而不是列表行：收藏这个动作天然发生在**听的时候**；
这一页不滚动，大按钮不会带回列表那边刚修好的误触问题。

控制栏 6 格 → 7 格（45px），**不挤掉任何现有功能**。
★ 用 CJK 字体子集里的字形 —— LVGL 内置符号既没有星也没有心。

### 7.2 今日 / ★ 两个视图

标签栏 3 → 5。前三个是**浏览维度**，后两个是**筛选子集**。

⚠️ `importedAt` 为 0 表示"写入时 RTC 没同步、不知道何时导入"，**不是 1970 年**，
所以 0 一律不算今天。

⚠️ 一次性现象：今天索引因哈希改版整个重建，所有记录的 `importedAt` 都被写成
今天，"今日"视图今天会显示全部曲目，明天恢复正常。

### 7.3 行内 ★ 标记

用的正是删掉封面小图标腾出的位置。**纯显示、不可点击**，不会带回误触问题。
歌手标签固定左移 14px 让出槽位 —— 不管有没有收藏都让，否则右边界参差不齐。

### 7.4 状态栏云朵：后台同步终于可见

每日同步此前**完全不可见**，只能从串口看。一个每天跑 30 分钟、会写 SD、
会占网络的后台任务，用户应该能一眼知道它在干什么。

| 云朵 | 状态 |
|---|---|
| 看不见 | 不可用（没联网 / provider 未配置） |
| 暗灰 | 空闲，今天已完成 |
| **亮青** | **正在下载**（唯一的亮色，"发亮就是在下"） |
| 橙 | 因电台在播而推迟 |
| 品红 | 空间不足停下 |

⚠️ 第一版把"不可用"设成 `kInkFaint`、"空闲"设成 `kInkDim` ——
**两种深浅相近的灰在 16px 图标上根本分不出来**。按"有几个状态配几个颜色"
分配，没考虑相邻深度在小尺寸下不可辨。改成不可用直接隐藏。

**图标是自绘的**（按用户给的参考：青云 + 橙圈白箭头），16×16
**ALPHA_8BIT（只存形状不存颜色）**：颜色要表达状态，彩色图 recolor 会被整体
混成单色块，双色设计反而丢了；alpha 掩码天生是"形状 + 外部着色"。成本 256 字节。

⚠️ **内联在 `hifi_ui.cpp` 而不是新建 `.c`**：`src/CMakeLists.txt` 用
`GLOB_RECURSE`，新增任何文件都触发 CMake 重配 + **约 16 分钟全量重编**
（实测 956 秒）；只改 `hifi_ui.cpp` 是 **67~77 秒**。

画的过程试错两次：照搬"圆圈内箭头"在 16px 下只有 5px 完全读不出，去掉外圈；
竖杆和三角在 y 方向重叠会叠成菱形，竖杆必须**止于**三角底边。

### 7.5 顺带修掉的显示 bug

`audio.getCodecname()` 在**没有播放时返回字面量 "unknown"**，代码直接抄进快照，
状态栏常驻显示这一串（还和云朵叠在一起）。没在播就给空串。

**这个 bug 一直都在，只是右边原本是空的没人注意 —— 加了图标反而把它暴露出来。**

## 9. 本轮工程教训（新增）

1. **用户的一句现象描述可能顶得上一整轮排查。** "电台卡、本地不卡"一句话排掉了
   SD 争用这个最大嫌疑。**转述时不要替他把话说重**（"很卡" ≠ "挂了"）。
2. **代理指标会骗人。** `zero=0` 只说明"采样时刻没观测到"，而我的采样恰好
   排除了故障时刻。指标和现象冲突时，**以现象为准**。
3. **先确认调用点再下结论。** 两次说"找到了"都是没查调用点就断言，
   一次是 `libraryCleanerAssess`，一次是周期日志。
4. **排除实验比继续猜便宜。** 关掉诊断日志做 A/B 花一次编译，
   但直接否掉了一整条错误路线。
5. **注意"这个量在别的场景下正常值是多少"。** 25% 水位对本地播放是安全线，
   对电台是常态线；`LONG_DOT` 在有高度约束时是省略号，没有时是换行。
6. **n=1 不是结论**（本轮又犯一次：`lang=zh` 打一发就下判断）。
7. **修好一处要顺手看同类的另一处**（本轮犯两次：R6 关了漏 Phase 4 自测；
   曲目行加了守卫漏分组行）。
8. **同一功能有多个入口时，策略要放在共用层。** 限速放对了（`downloadToFile`），
   让路放错了（只在 daily_sync），于是脚手架绕过了它。
