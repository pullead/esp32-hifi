## 1. Phase 4：单首下载闭环（已验证）

`src/discovery/download_manager.{h,cpp}`：HTTP 流 → 2KB 分块 → SD，
先写 `.part`、长度校验通过才原子 rename。下载前先算空间。

串口实测：

```
[DL][TEST] try1/3 http_error 0KB/0KB 1788ms  http=500
[DL][TEST] try2/3 ok       3416KB/3416KB 150695ms http=200
   -> /music/tracks/jamendo_1593988.mp3
```

整条链路通了：HTTPS → JSON → 候选 → 跳过坏曲目 → 流式写 SD → 校验 → rename。

### 1.1 三个真问题（排查顺序即发现顺序）

**① `audiodownload_allowed` 不是 `/tracks/` 的合法查询参数。**

```json
{"headers":{"status":"success","code":0,"error_message":"",
 "warnings":"The following parameters are not recognized for this method:
             [audiodownload_allowed]","results_count":0},"results":[]}
```

Jamendo 收到它会警告并返回空数组，而且**时灵时不灵**——同一个 URL 有时
5 条有时 0 条。去掉即可：可下载与否的过滤本来就在解析器里按**响应体**中的
同名字段做（那是合法的响应字段）。

⚠️ 我一度把这个现象判成"服务器一过性故障、已自行恢复"，**是错的**。当时没有
证据就下了结论。真正定位靠的是新加的 `[JAMENDO][RAW]`：解析出 0 条时把响应
前 300 字节原样打出来。**这行日志成本是零，价值是省掉一轮 20 分钟的编译。**

**② `audiodownload_allowed=true` 不保证真能下载。**

同批候选里 `id=2034080` 的下载地址**恒定 HTTP 500**（PC 直连 `curl` 复现，
排除板子和 TLS 的嫌疑），而 `1593988` / `1932670` 正常 206。
API 层的授权标志和存储层的可用性是两回事。

分叉点靠 PC 侧 `curl` 定的，没浪费烧录：

```
id=2034080  http=500 size=0
id=1593988  http=206 size=1024
id=1932670  http=206 size=1024
```

**③ 停滞超时只覆盖了"一个字节都没收到"的情况。**

原判据 `millis() - startMs > 15000 && bytesWritten == 0` 有两个漏洞：
- 传到一半断流：已经写了字节，判断永远不成立，无限空转
- 服务器不给 Content-Length（chunked/keep-alive）：`expectedBytes=0`，
  "收满就退出"永远不触发，**下完了也会一直挂着等**

改成按"距上次收到数据多久"算（`kStallTimeoutMs = 20s`）。
同时区分 `cleanEof`：没给长度又不是干净结束时，**不能认为文件完整**，
否则半截 mp3 会通过 rename 进曲库。

⚠️ **这条路径至今没有实测触发过**，只验证了它不会误杀慢速传输。不算已验证。

### 1.2 观测性补强（同一类教训）

| 补的东西 | 不补的话会怎样 |
|---|---|
| 早退路径的 `elapsedMs` | HTTP 错误报成 `0ms`，看着像瞬间失败，实际等了 1788ms |
| 每 512KB 一行进度 | "慢"和"卡死"在串口上完全同形——我因此误判过一轮 |
| 候选为 0 时写 `no candidates` | `[DL][STATE]` 是空行，"没结果"和"没运行"分不出来 |
| `[JAMENDO][RAW]` | 只能靠猜，见 §1.1① |

## 2. R6：边播边下的争用（已验证）

不靠"听着好像没卡"，用 `audio.inBufferFilled()` 按 100ms 采样。

### 2.1 本地音乐播放

```
base(avg=99% zero=0 low=0            n=150)
dl  (avg=86% zero=1 low=105 maxrun=1 n=1483)
```

余量够用但被明显吃掉一块：归零仅 1 次且 `maxrun=1`（单个孤立采样，形态符合
切歌而非持续饥饿），但 7.1% 的样本掉到容量 25% 以下，基线是 0。

### 2.2 电台播放（下载对它影响为零）

```
cap=639KB
base(avg=40% min=38% zero=0 low=0            n=150)
dl  (avg=40% min=37% zero=0 low=0 maxrun=0   n=1478)  147698ms
```

无 mbedTLS 分配失败、无崩溃。

> ### ⚠️ 2026-09-05 更正：本节"影响为零"的结论是错的
>
> 用户实测反馈：**后台下载时电台明显卡顿，本地音乐不卡。**
> 复测拿到直接证据（同一套探针，条件不同）：
>
> ```
> base(avg=26% min=18% zero=0 low=45  n=150)
> dl  (avg=37% min=0%  zero=9 low=594 maxrun=3 n=5628)
> ```
>
> **电台缓冲触底 9 次**，最长连续 3 个采样（约 300ms）。
>
> 上面那组 `zero=0` 之所以没测到，是因为探针有两个缺陷：
> 1. **采样只在 `audio.isRunning()` 为真时进行** —— 若卡顿瞬间该标志变假，
>    那些样本会被直接跳过，**测量在系统性排除它本该捕捉的现象**。
> 2. **100ms 采样间隔太粗** —— 一次可闻的欠载只需几十毫秒。
>
> `zero=0` 的真实含义是"**在采样时刻**没观测到归零"，不等于"没发生过欠载"。
> 我把它当成了后者。详见 §10。

### 2.3 被推翻的一个结论

曾记录"下载会让自己变慢 25%"（空闲 144s vs 播放中 180s）。
后续两轮：空闲 169s vs 播放中 150s、空闲 209s vs 播放中 190s——**方向相反**。
下载耗时被网络波动主导，争用的影响淹没在噪声里。
**那条是把 n=1 当成结论，不成立。**

### 2.4 三个我自己造成的测量缺陷

1. **前置条件互相矛盾。** 空闲下载要求 `!audio.isRunning()`，R6 要求正在播放，
   我却把 R6 挂在"空闲下载成功"上。结果用户按要求提前播放时，两个都被跳过。
2. **只有 min/starv，分不出"切歌归零"和"真饿着"。** 补 `zeroCount` /
   `lowCount` / `maxConsecZero`，靠形态区分。
3. **基线取早。** 电台起播后缓冲还在填，15 秒基线量到 16%，而 190 秒的下载
   窗口量到稳态 46%，造出"下载让水位变高"的假象。加 20 秒稳态等待后
   base/dl 都是 40%，吻合。

## 3. 自适应节流

下载搬运时盯着解码输入缓冲，吃紧就多让步。回调注入，下载模块不依赖播放器实现。

### 3.1 第一版判据是错的

按**绝对水位**标定（危险 <25%、偏低 <50%），拿本地播放的数据定的。
换电台一测就崩了假设：

| 音源 | 稳态水位 | 25% 这条线的实际效果 |
|---|---|---|
| 本地播放 | 99%（从 SD 预读填满） | 只在压力下触发 ✅ |
| 电台 | 40%（按网络供给即时消费） | **一直触发** ❌ |

实测 469 次让步里绝大部分是无谓的——电台自始至终 `zero=0`，没有任何危险。

**根因**：把"绝对水位"当危险信号，但这个量在不同音源下的正常值差了一倍以上。

### 3.2 改成看趋势

**低且还在往下掉**才让步（`<8%` 时无条件）。稳定在低位不算危险，正在被抽干
才算。自适应，不需要针对音源调参。

效果：`469x/4265ms` → `92x/460ms`，降到约 1/5，依然零饥饿。

## 4. DMA 内部 RAM 的真实构成

起因是用户问："只剩 7KB 会不会卡？新功能能不能做到几乎不吃 DMA RAM？"

开机各阶段 `dma_free`：

| 阶段 | dma_free | 该阶段消耗 |
|---|---|---|
| runtime_start | 167 KB | — |
| after_sd_init | 155 KB | 12 KB |
| after_wifi_connected | 101 KB | **53 KB（WiFi）** |
| after_audio_set_pinout | 30 KB | **70 KB（音频）** |
| after_lvgl_init_and_home_screen | **6.3 KB** | **24 KB（LVGL）** |

运行时（电台 + 下载并发）：`dma_free_min=2792B`、`dma_block_min=1984B`。

### 4.1 结论：方向对，目标错

吃掉 DMA RAM 的是**开机时固定分配的三样东西**，合计 147KB。
下载功能的边际成本只有几 KB。

用户设想的四项里：
- JSON 候选、曲库元数据（750KB 索引）→ **本来就在 PSRAM**
- 封面 → 还没实现，实现时放 PSRAM
- 下载分块缓冲（`uint8_t buf[2048]`）→ 在**任务栈**上，**搬走省不下东西**，
  那 10240 字节的栈无论如何都已经分配了

配置现状：`SPIRAM_MALLOC_ALWAYSINTERNAL=1024`（>1KB 自动进 PSRAM）、
`SPIRAM_TRY_ALLOCATE_WIFI_LWIP=y`、`MBEDTLS_EXTERNAL_MEM_ALLOC=y`。

### 4.2 一个我在没测量时提出、拿到数据后否掉的建议

我曾说调 `SPIRAM_MALLOC_RESERVE_INTERNAL`（当前 0）是"比搬缓冲更值钱的杠杆"。
**拿到数据后不成立**：那个配置防的是零散小分配啃光内部 RAM，而实测消耗几乎
全部来自驱动初始化的大块分配。改它收益很小，还会把小分配推去较慢的 PSRAM。
**不改。**

顺序错了——先给建议后测量。

### 4.3 唯一真正的杠杆（暂不动）

LVGL 的两个刷新缓冲 2 × 10240 = 20KB，是应用能控制的最大一块。
降到 8 行能省 10KB（≈ 当前空闲 DMA RAM 的 1.6 倍）。

**建议暂不降**：实测电台播放完全不受影响，也没有任何分配失败。
6.3KB 虽薄但**稳定**——开机后系统不再申请大块 DMA 内存。
等真出现分配失败再动它，那时也有明确证据。

## 5. USB DAC：Windows 出声首次真正验证

`§1` 曾记录本项目最贵的教训——"在 Windows 上验过"一度是**从未实测的口头
声称**。后来补的实测只到枚举层（`Status=OK` / `problem=0`），证明设备被正确
识别，不等于声音出来了。

**本次用户实测确认：能听到声音。** 这一格终于填上了。

主机侧（USB-OTG 接管 D+/D− 后串口不可用，只能这么查）：

```
USB\VID_303A&PID_1001\1CDBD47B51E8              OK  problem=0   <- 设备本体
USB\VID_303A&PID_1001&MI_00\7&3A8250E8&0&0000   OK  problem=0   <- 音频接口
AudioEndpoint「ヘッドホン (2- MiniWebRadio DAC)」  OK
Win32_SoundDevice「USB Audio 2.0」               OK
```

⚠️ **排查要点**：`Get-PnpDevice` 会列出一堆同名 `Status=Unknown` 条目，实例 ID
各不相同（`6&23872D18`、`7&89DCC56`、`7&372C3057`……）。那是历次插拔留下的
**幽灵注册表项**。只看实例 ID 与当前父设备一致的那几条，否则会误判成设备有问题。

据此把 `sdkconfig.esp32s3` 里那段 TinyUSB shim 提交掉（它是误跑全环境
`pio run` 时 ComponentManager 加回 tinyusb 产生的，此前一直悬着）。

仍未验证：macOS/Android 声音连续性、iPhone 音量滑块、96k/24bit。

## 6. Phase 5：每日发现同步（已实现，端到端未验证）

`src/discovery/daily_sync.{h,cpp}`。设计被前面几轮实测直接约束：

| 约束 | 来源 |
|---|---|
| 单曲失败要跳过并记账，不能终止整轮 | §1.1② |
| 一次拉空 ≠ 今天没歌，要重试、换 offset | §1.1① |
| 一首 150~210 秒，10 首要 25~35 分钟 → 必须后台长任务 | §1 |
| 边播边下安全，**不做**"只在没播放时下载" | §2 |
| 空间不够就停，**不删任何文件** | 真实删除需单独验证+用户确认 |

实现要点：
- 语言配额 中3/日3/英4 + **回填档**。中日曲目稀少是已确认事实，
  回填是**主路径**不是异常分支。
- 去重按 `provider + providerTrackId`。
- **offset 逐轮推进并持久化**。不存的话每天从 0 拉，第二天候选和第一天几乎
  一样，全部命中"已拥有"然后空跑一轮。
- 索引存盘在**整轮结束后一次性**做。2000 × 384B ≈ 750KB，每首存一次会把
  一轮同步变成 10 次大写盘。
- `dailySyncDue()` 在 RTC 未同步时返回 false，且启动时必须从 NVS 读回
  `lastRunDay`——否则**每次重启都算新的一天**，反复下载。

首轮验证 `kDailySyncTracksPerDay = 3`（`src/main.cpp`），
**验证通过后要改回 10**。

### 6.1 一处写错后改掉的

原本在下载成功后追加一条"导入事件"。**事件类型里根本没有导入这一项**，
而且导入已由 `importedAt` 字段和索引记录，回放一条导入事件什么也做不了，
只会给每首歌多一次 SD 写。已去掉。

## 7. ⚠️ 未解决：电台点击无反应（本轮收尾时发现）

**现象**：烧录 Phase 5 固件后，用户点击电台**没有反应**，播不起来。

**状态：未定位。** 以下都是待验证的假设，**不要当成结论**：

1. **同步任务与电台起播争资源。** 电台起播要新建 HTTP/TLS 连接，而实测
   `dma_block_min=1984B` ——若此刻同步正在下载，分配可能失败。
   但 §2.2 明确测到过"下载期间电台播放正常"，所以**至少不是简单的
   '下载就播不了'**；起播（新建连接）和已在播（维持连接）是两回事。
2. **索引存盘的 750KB 大写盘阻塞。** 这是本轮新引入的最大单次 SD 写。
   Phase 1 正是在 SD 写上翻过车（写在了播放启动路径里）。
3. **同步任务异常退出/卡死**，占着某个共享资源没放。
4. 与 Phase 5 无关的其他回归。

**排查起点**（下次优先做）：
- 复位后**不要让同步触发**（断网，或临时把 `kDailySyncTracksPerDay` 设 0），
  确认电台是否恢复正常 → 这一步就能把范围切成"Phase 5 引入"还是"别的"。
- 抓电台起播时刻的串口，看有没有 `mbedtls` / `alloc failed`。
- 看 `[SYNC][STATE]` 当时处于哪个阶段（running / done / 卡住）。

## 9. 工程教训（本轮新增）

1. **没有证据就不要下结论。** "服务器一过性故障、已自行恢复"这句话让我多绕了
   一轮，真相是 URL 里有个非法参数。
2. **先测量后建议。** `SPIRAM_MALLOC_RESERVE_INTERNAL` 那条建议是在没数据时
   给的，拿到数据就被自己否掉了。
3. **n=1 不是结论。** "下载慢 25%" 被后续两轮直接推翻。
4. **实验的前置条件要自洽。** 两个互相矛盾的前置条件让整个 R6 被静默跳过。
5. **阈值要问"这个量在别的场景下正常值是多少"。** 25% 对本地是安全线，
   对电台是常态线。
6. **构建命令要带 `-e esp32s3`。** 漏掉一次触发全环境构建，改动 17 个组件、
   清掉 IDF 子工程、删掉 `bootloader.bin`，把 2 分钟增量变成 20 分钟全量。
   （后续烧录改成只写 `0x10000` 的 factory 分区绕过重建。）
7. **heredoc 里的反斜杠会被吃掉。** 今天 8 次 `\n` 被写成真换行拆断字符串，
   两次导致编译失败。对策：含 `\n` / `\"` 的代码一律用 `chr(92)` 拼接或
   占位符替换，不直接写反斜杠。

## 10. 2026-09-05：电台卡顿 —— 定位与处置

### 10.1 用户观察推翻了 §2.2

**"电台卡、本地音乐不卡"这半句是全部线索的关键。**

- 若瓶颈在 **SD 争用**：本地播放要读 SD、下载要写 SD，该卡的是**本地音乐**；
  而电台**根本不碰 SD**。
- 现象正好相反 ⇒ **机制不在 SD**。

剩下的差异是电台独有的那条路径：持续的网络接收。

### 10.2 机制：DMA 内部 RAM 被压到 160 字节

昨天补的"基线 vs 下载中"对照字段第一次派上用场：

| | 空闲基线 | 下载中 |
|---|---|---|
| DMA 空闲总量 | 5616 B | **836 B** |
| **最大连续块** | 4352 B | **160 B** |

WiFi 接收路径需要 DMA 可用的内部 RAM —— 而这正是**电台依赖、本地 SD 播放
不依赖**的东西。这解释了那个关键差异。

⚠️ 这是**测到的相关性 + 合理机制，不是证明**。
（此前猜的是 TLS 解密抢 CPU，证据不如这条强。带宽早就排除了：
电台 16KB/s + 下载 23KB/s 对 WiFi 毫无压力。）

### 10.3 两层处置

**策略层**（`daily_sync.cpp`）：电台在播就**不开新的下载**，最多等 10 分钟，
还在播就推迟这一轮。每日同步有 24 小时可用，用户的听感只有一次。

**安全网**（`download_manager.cpp`）：下载**途中**电台才起播时，限速到
`kNetAudioRateCapBps = 6KB/s`。不硬停 —— 长时间闲置会被服务器关连接，
反而让已下的部分白费。

⚠️ **推迟 ≠ 今天跑过了**，所以不记 `lastRunDay`，主程序 15 分钟后重试。
否则用户听一下午电台就等于当天曲库完全不更新。

### 10.4 验证结果

| 项 | 状态 | 证据 |
|---|---|---|
| 6KB/s 限速生效 | ✅ | 3416KB / 570931ms = **6.0 KB/s**，与设定精确吻合 |
| 电台在播时不开新下载 | ✅ | 200 秒内 `attempts` 冻结在 3 不动 + `deferring download` 日志 |
| 用户听感 | ✅ | 用户确认"感觉没啥卡顿了" |
| **电台缓冲仍会触底** | ❌ | 限速下仍 `zero=9 maxrun=3` —— **限速能减轻但没消除** |

最后一行是保留 §10.3 策略层的理由：**只靠限速不够，得干脆不下载。**

### 10.5 三个自己造成的问题

**① R6 测试脚手架成了负担。** 它挂在 `jamendoProbeTask` 末尾，导致：
- `probe_done` 要等它整个跑完才置位，**卡住每日同步 10 分钟**
- 它直接调 `downloadToFile`，**绕过 daily_sync 的让路策略** —— 正是要避免的事

根因：**同一个功能有两条下载入口，我只在其中一条上加了策略。**
限速放在 `downloadToFile`（所有入口共用，对的）；让路放在 daily_sync
（只覆盖一条）。现已把 R6 阶段用 `kRunR6Experiment = false` 关掉。
⚠️ 若将来再加下载入口（手动同步按钮、封面下载），同样问题会重演。

**② 触发条件不满足时完全静默。** 一轮 12 分钟的抓取里一行 `SYNC` 都没有，
却看不出是哪个门没过。补了 `[SYNC][STATE] idle rtc=… probe=… due=… force=…`
后**一眼就定位到 `probe=0`**。
这个毛病在 `[DL][STATE]` 上修过一次（"没结果"和"没运行"分不出来），
同一个功能的触发路径上又犯一遍。

**③ 抓取时序安排错了。** 烧录即复位 → 同步在开机 30 秒后触发 → 用户此时还没
开电台 → 下载在"没电台"的窗口里就跑完了 → 抓取只看到累计结果，
既证明不了有效也证明不了无效。**验证并发行为时，被测的两件事必须都在
观测窗口内开始。**

### 10.6 遗留

  `dailySyncDue()` 在 RTC 未同步时返回 false，同步永远不会跑。** 独立问题，未查。
- ⚠️ **两个测试专用开关必须改回去**：
  `kDailySyncForceOnBoot = true` → `false`；`kDailySyncTracksPerDay = 3` → `10`。
- 🟡 Phase 5 一轮完整同步仍未跑完（`got=2/3`，第 3 首因电台在播而推迟）。
- 🟡 DMA 最大连续块在下载时低到 160B。有了让路策略后不会和电台重叠，
  但**下载本身仍会把余量压到这么低**。§4.3 曾建议不动 LVGL 那 20KB 刷新缓冲
  （理由"薄但稳定"），有了 160B 这个数，该建议值得重新评估 —— 但不急。
